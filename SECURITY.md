The Bun server serves Better Auth and the notebook API on the same origin. Database credentials and signing secrets remain server-side. Every private request checks the session and the server-owned role, active state and expiry. Teachers can read and edit attendance, notebook notes and profile fields for active assigned students. Grade data, roster assignments and account management require the Administrator role. Students receive only their own projected attendance. See [roles](docs/roles.md) and [Railway setup](docs/railway-setup.md).

Administrators cannot change their own application access, disable themselves or reset their own password from account management. Personal profile settings let approved users change their own display name and photo through the current Auth session; these updates cannot change roles, assignments or another identity. Photos use bounded PNG, JPEG or WebP data URLs with server-side size and signature checks; the browser resizes uploads before saving. Signup cannot inject a photo. No new storage tables or public upload URLs are used.

Administrators can reset another credential account's password from Settings. The server generates a random replacement, stores the hash and deletes the recipient's sessions in the same transaction. The plaintext appears in the one reset response with `Cache-Control: no-store` and stays in the administrator's browser memory until the message is dismissed. Administrators deliver the message privately. The existing MCP password reset, private CLI bootstrap and recovery remain available.

Events are append-only through the API. Pending batches can contain private student information in browser storage; reconcile uncertain delivery before clearing storage. Revocation cannot retract data already downloaded; an idle view clears on the next denied request. Keep real accounts, records, credentials and private snapshots out of Git, logs, screenshots and recorded traces. Live checks use synthetic fixtures with tracing disabled and clean up afterward.

[Railway setup](docs/railway-setup.md) covers deployment and recovery. Preserve the Neon source services and data and backup branch `backup/neon-current-2026-11-15` (`77cedae`). Local and synthetic tests do not prove live provider behavior.

The frontend CSP permits three exact SHA-256 style hashes for dnd kit 0.5.3's feedback, grabbing cursor and selection rules. Arbitrary inline styles remain blocked. When upgrading dnd kit, regenerate hashes from its exact emitted style text and verify the actual dragged pill position under the production CSP; ordering alone does not prove the preview works. The synthetic table browser scenario asserts that visual geometry.

## MCP access

MCP uses audience-bound OAuth tokens stored as hashes by the Better Auth provider. The resource checks the token, originating session and current application permissions before presenting tools or handling them. Browser API credentials stay in the site session. Client ID metadata uses a DNS-pinned public HTTPS connection and OAuth authorization parameters are signed during browser sign-in and consent. Store client credentials and tokens privately. See [MCP setup and permissions](docs/mcp.md).

## Account invitations

The device account chooser lists identities with live Better Auth sessions held in this browser. Session credentials stay in signed HttpOnly cookies, with Secure on HTTPS. Switching validates the target session and sets the active cookie. The chooser returns only user IDs, names and login identifiers. Application APIs continue to authorize the active identity and its role. Personal profile updates check the expected identity, and password rotation or session expiry invalidates the saved login.

Administrator-created invitations generate a random starter password and store its Better Auth hash. The browser invitation form receives the plaintext in the creation response. The administrator confirms ownership directly with the recipient. The server stores a unique normalized sign-in phone, separate from personal and roster contact information. Phone sign-in still requires the account password and an active, unexpired grant. Personal edits cannot set the sign-in phone. Invited users must finish setup before accessing private application records. Password changes revoke all sessions for that user, including the setup session. Application roles and roster links remain administrator-owned.

MCP invitation provisioning stores the message encrypted with AES-GCM in the existing Auth verification table in the same transaction that creates the account. The encryption key is derived separately from the server signing secret. The receipt expires after 15 minutes. Its URL reference grants no access by itself. A same-origin browser POST checks the creating user's active session and current administrator access, then consumes the receipt atomically. The one successful response uses `Cache-Control: no-store` and the viewer keeps the result in memory. The MCP tool, card and chat receive only the link and reference. The recipient's starter password remains valid until changed or reset.
